## 13. Step 5: backend skeleton (FastAPI + uvicorn)
- POST /api/decks: accepts a PDF, checks size (25 MB) and the %PDF header,
  saves it under a random 8-character id (the uploaded filename is never used
  as a path), renders JPEG slides. Tested via /docs: 200, 13 slides.
- FastAPI = application logic; uvicorn = the server that listens on the
  port and passes requests to it (ASGI).


- Why uvicorn: it is FastAPI's default and best-documented server, supports
  async, and needs no config. Alternatives: Hypercorn (HTTP/2-3), Daphne
  (Django), Granian (Rust), Gunicorn (process manager, can run Uvicorn
  workers). Not benchmarked: server speed is irrelevant here because the
  Gemini calls take seconds.
- Constraint: in-memory job progress needs a single worker process.


## 14. Step 6: analyze job with progress
- POST /api/decks/{id}/analyze starts a background job and returns a job_id
  at once; GET /api/jobs/{id} reports status, slides_done and a per-slide
  timeline. Reason: an analysis takes 15 s to minutes, too long for one request.
- deck_id from the URL is validated (8 hex chars) to prevent path traversal.
- Job progress is in memory: lost on restart, needs a single worker.
  Planned fix: move it to the database (Step 7).
- Per-slide start/end times are stored to check whether calls overlap.

## 19. Database decision: SQLite (built-in sqlite3, plain SQL)
- Why: zero setup (single file), SQL is familiar from Postgres, data volume is
  tiny, single worker is enough.
- Rejected: JSON files only (no querying for lists and tracking), Postgres

- Risk: free hosts may have a temporary disk (restart can wipe app.db and
  uploads). Not yet checked for any specific host. Options at deploy time:
  persistent disk (may cost) or free hosted Postgres.
- Mitigation: all SQL lives in one file (db.py), so moving to Postgres means
  rewriting that file only.

## Limitations (to reuse in the one-page summary)
Method
- Scores come from a language model and vary between runs (same deck, model,
  prompt: 92.0, 92.0, 92.0, 90.2, 90.2; one criterion, roadmap_gtm, moved
  5 -> 4). Small sample.
- Weights are provisional (author's choice), not from a published source.
  The rubric source ("10-12 core slides" guidance) is still to be cited.
- Reading and scoring are two model steps, so a transcription error can flow
  into the score; icon-only information (ticks, colours) is lost between
  them (e.g. competition table).
- "Quote found" compares the quote with the model's own transcription, not
  the slide image, and does not prove the quote supports the score. The
  justification text is not checked (one invented "logo placeholder" seen).
Data
- The test deck is synthetic and was written by Gemini, then scored by
  Gemini (self-preference risk); scores sit near the ceiling, so stability
  may be overstated. Real decks and human scores come from the evaluation.
- Free-tier prompts may be used by Google to improve its products; only
  synthetic or openly published decks are used.
Reliability and speed
- Latency varies widely (20 s to 93 s, plus one failed run and several
  timeouts); the hosted model and its quota are outside our control.
- Results depend on the model version and the date; every run stores its
  model name and settings.

## 29. Step 12: evaluation tools
- Tables human_scores and deck_sources (public URL, synthetic flag).
  Synthetic decks are excluded from metrics; non-synthetic need a URL.
- Metrics: exact agreement, within +-1, MAE, bias (model minus human),
  baseline = always predict the median human score (constant; no keyword
  baseline built), consistency across runs (share of identical scores, mean
  spread, match% range per deck).
- Process: score each deck in a PDF viewer BEFORE uploading (the Analyzer
  shows the model's % immediately); type scores in before opening the report.
- Limits: baseline weights each deck once, model weights each run; keep runs
  equal across decks; 8-10 decks is a small sample.


## 30. Rate limit found (429 RESOURCE_EXHAUSTED) and fix
- Error: "Generate content requests per minute limit exceeded on Free Tier",
  model gemini-3.1-flash-lite, quotaValue 15, retry in ~22 s.
- AI Studio limits for gemini-3.1-flash-lite (free tier): RPM 15, TPM 250K,
  RPD 500. Observed peaks: RPM 18/15 (exceeded), TPM 20.85K, RPD 107.
- Cause: one analysis = 14 requests (13 reads + 1 score), so two analyses
  within a minute exceed 15 RPM ("Run 2 more times" ran them back to back).
  Retries had been 1 s apart (the improved retry fix was not applied), which
  added more rejected requests.
- Fix: shared rolling-window RateLimiter (14 per 60 s; lower to 12 if 429s
  persist) before every Gemini call, 25 s wait on 429, retry only retryable
  errors, status code in the log line, cancel sibling tasks on failure.
- Consequences: back-to-back runs take about 1 minute each; daily budget of
  500 means about 24 analyses per day with margin (8 decks x 3 runs).
  Unknown: whether rejected requests count towards the daily limit.
- Demo note: one analysis uses 14 of 15 requests per minute; do not start a
  second one (or click several feedback buttons) within a minute.



## 31. Why the evaluation exists
- The analyzer alone is not new (similar tools exist). The contribution is a
  reliability study: agreement with human scores (exact, within +-1, MAE,
  bias), comparison with a constant baseline, and consistency across repeated
  runs.
- Evaluation is a research tool for the author and the supervisor, not a
  founder-facing feature. Indirect value for founders: it says how much the
  percentage can be trusted (noise level, bias, which criteria are stable).
- Results are not known yet; a sample of 8-10 decks is small, and a
  "not very reliable" finding is still a valid result.
- Possible later: per-criterion stability notes on the Report page.
